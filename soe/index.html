01Live

AI ticket operations

A 24/7 customer-facing agent classifies each request, assembles context, researches the answer, and either resolves the ticket or prepares a controlled human handoff.

  • Explicit authority boundaries
  • Policy-mandated escalation
  • Dedicated identity and audit trail
How it works+

Problem A model can pass an offline test and still fail in production when the real execution path, credentials, tools, or cost behavior differ.

Implementation The ticket agent and wider support-ops agents run different models behind a provider-neutral runtime, so model choice stays a scored pass-rate-versus-cost decision rather than an architecture change. Each ticket emits a PII-masked trace at the orchestrator layer, with dedicated credentials, per-ticket cost accounting, and a circuit breaker that halts an all-error batch.

Validation Changes move through a 250-case production suite spanning core support categories and security scenarios, then shadow or private-note replay, live-path probes, staged activation, and rollback controls. A real cutover exposed that evaluation and production invoked the model through different execution paths - SDK versus CLI - so production parity became a release requirement rather than a one-off fix.

02Live + evolving

Workflow automation

Zendesk APIs, side apps, Slack interfaces, and orchestrated workflows connect ticket work with warranty, orders, shipping, and internal operations.

  • Regional warranty coordination
  • Human approvals for consequential actions
  • Versioned logic and runbooks
How it works+

Problem Mature n8n workflows carry real side effects. Rewriting them wholesale would trade visible complexity for hidden migration risk.

Implementation I keep n8n where visual orchestration is the better tool and move decision-heavy paths into versioned code when they need tests, replay, and diffs. The live RMA flow spans Zendesk, Jira, Slack, registration, returns, and internal review branches. Ports begin by pinning the existing input-output contract, then comparing the same cases in shadow before authority moves.

Validation The current 82-node RMA workflow completed 99 of its latest 100 recorded runs successfully when reviewed on August 5, 2026. Code migrations preserve the previous workflow as a rollback target. A stronger approval layer - exact-draft binding, actor checks, and timed escalation - shipped dark behind feature flags with 52 new tests; activation is gated separately.

03Live

Knowledge infrastructure

A governed, versioned knowledge layer serves both people and AI, while hybrid search retrieves by symptoms, products, firmware, and exact error strings.

  • Lifecycle ownership and freshness
  • Help Center and agent retrieval
  • Access control before model context
How it works+

Problem Dense retrieval could be semantically close but operationally wrong, such as ranking firmware content above a refund policy. Prompt rules also cannot reliably protect restricted knowledge after it reaches model context.

Implementation A confidence gate keeps fast dense retrieval on the common path, then escalates uncertain searches to multi-query dense + sparse retrieval fused with reciprocal rank fusion. The Help Center index is built only from anonymously accessible Zendesk articles, chunked with overlap, embedded in batches, and tagged with lifecycle metadata before upsert.

Validation The sparse encoder is pinned to the index-writer contract with a deterministic self-test; a kill switch returns the system to dense-only search. After the June 17, 2026 change, the reported refund, warranty, and firmware failure clusters returned the correct source in 5 of 5 verification runs - a narrow post-change check, not a global accuracy claim.

04Live + expanding

Quality & operating intelligence

A production evaluation suite, approval gates, monitoring, and support signals show whether the system is safe, healthy, and improving in production.

  • 250 cases across 11 support categories
  • 25 adversarial cases across 16 security themes
  • Every failure becomes an owned change
How it works+

Problem A good-looking reply does not prove the agent took the right action, and observability without an owner or response loop is only a dashboard.

Implementation PII-masked Langfuse traces record each ticket's input, execution path, outcome, latency, model, error, and self-reported gap. An hourly tripwire watches outcome failures; a daily review routes behavior, knowledge, policy, and infrastructure findings to different owners. Confirmed DSAT root causes cannot close without a regression case.

Validation The first trace-driven review found a multi-day provider-quota outage that return-code health checks had missed. The permanent fix added outcome-based health, dedicated-key isolation, capacity preflight, bounded retries, and recovery verification. Reply evaluation is live; trajectory and end-state evaluation are designed but not yet in production.

Evidence boundary These notes are distilled from private production repositories, merged pull requests, evaluation artifacts, and live workflow execution history. Customer data and proprietary code are not published.

02 / Decisions and permanent change

Six times production disproved me - and what became permanent.

I personally built the AI support operation: the original n8n-based email agent and the first versions of nearly every component in today's system. As it matured, I handed defined AI maintenance areas to two specialists; our automation specialist primarily builds process automation. I still set the architecture, authority boundaries, evaluation bar, release gates, and incident response, and I own what happens in production. These six cases show how that ownership works.

01 MeasurementI was measuring the wrong thing. Read case

The decision I treated final ticket ownership as the AI handoff metric and planned toward an 80% AI-resolution target.

The signal Final ownership missed mid-ticket human intervention, while many apparent failures were correct warranty or authority escalations.

The correction I separated AI-attempted capability from handoff quality instead of optimizing one proxy.

What became permanent The roadmap moved from sequential automation gates to dual-track execution governed by customer and operating outcomes.

02 QualityA flattering quality score contradicted customer outcomes. Read case

The decision Our audit rubric rated the AI above the human team.

The signal Its dissatisfaction outcomes were worse; the rubric rewarded polished responses without anchoring to customer satisfaction.

The correction I rejected the score and recalibrated the rubric around DSAT and explicit human-escalation failures.

What became permanent High-scoring dissatisfied tickets now flag calibration failure, and confirmed DSAT causes require a regression case before closure.

03 OwnershipI approved the policy, then crossed the implementation boundary. Read case

The decision A policy approval was treated as permission to push the implementation directly.

The signal The execution bypassed the specialist who owned the production agent.

The correction I ordered a rollback four minutes after the mismatch surfaced and reopened the work under the correct owner.

What became permanent Policy approval no longer grants implementation ownership; production changes route through the accountable specialist.

04 SimplicityMore rules made the AI less capable. Read case

The decision Two weak replies initially produced proposals for more keywords and mandatory gates.

The signal The rules were overriding semantic judgment and forcing customers to repeat steps they had already completed.

The correction I stopped the additions and separated hard safety and authority boundaries from reversible support judgment.

What became permanent We deleted the keyword table and replaced four rigid gates with principle-and-signal checks.

05 Release disciplineA passing evaluation did not mean production worked. Read case

The decision A model that passed the fixed evaluation set was cleared for staged production use.

The signal The first live batch failed because evaluation and production invoked the model through different execution paths.

The correction We stopped the rollout, proved one live path end to end, then recovered the queue in controlled stages.

What became permanent Live-path probes became a release gate, with isolated runtime configuration, shadow mode, rollback, and monitored cutover.

06 Outcome observabilityA green health check hid a failing customer pipeline. Read case

The decision Scheduled-job completion was treated as operational health.

The signal Trace review found multi-day reply failures while the process still returned successful exit codes.

The correction We restored capacity and recovered waiting tickets through controlled batches.

What became permanent Health now means per-ticket outcomes, backed by capacity preflight, an all-error tripwire, circuit breaker, rotating canaries, and transcript recovery.

The decisions show how I operate under uncertainty. The synthetic ticket flow shows the resulting control model.
